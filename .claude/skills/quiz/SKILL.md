# プロジェクト理解度クイズ

ユーザーが現在作業しているプロジェクトについて、一問一答形式のクイズを出題し、採点・記録するスキル。

## 目的

- ユーザーがプロジェクトのアーキテクチャ・設計判断・実装の勘所を**口頭で答える形**で復習できる
- 過去の苦手領域を継続的に追跡し、繰り返し出題することでキャッチアップする
- 学習履歴を `docs/quiz/` 配下に蓄積し、後から見返せるようにする

## 全体の流れ

1. **過去の記録を読む** — `docs/quiz/` を確認し、過去の苦手問題（△ や ✕）と既出領域を把握
2. **作問の根拠を集める** — `CLAUDE.md`、`docs/design/`、`docs/` 配下のドキュメント、必要に応じてコード自体
3. **出題範囲を決める** — ユーザー指定 > 過去の苦手領域 > 未出題領域 の優先順位
4. **一問一答で進行** — 1 問ずつ出題、回答待ち、採点、補足解説、次へ
5. **セッション終了時に記録** — `docs/quiz/{YYYY-MM-DD}.md` に保存

## ステップ詳細

### ステップ 1: 過去の記録を読む

セッション開始時にまず以下を実行：

```bash
ls docs/quiz/ 2>/dev/null
```

ファイルが存在すれば、**最新数件の結果サマリ表**と**「次回重点復習候補」セクション**を読む。これにより：

- 過去に △/✕ だった領域 → 今回優先的に出題
- 過去に ◎ だった問題 → 同じ問題は避けて、関連する別の角度から出題
- 「次回重点復習候補」 → そこから優先的に作問

過去記録がない（初回）場合はその旨ユーザーに伝え、プロジェクト全体から幅広く出題する旨を共有する。

### ステップ 2: 作問の根拠を集める

**主たる根拠：**

1. `CLAUDE.md`（プロジェクトルート） — プロジェクト概要・アーキテクチャ・規約
2. `docs/design/` 配下のすべてのマークダウン — 各サブシステムの設計判断
3. その他 `docs/` 配下のドキュメント
4. （必要なら）実装コード — 設計と実装の対応を問う場合

**作問のコツ：**

- **「なぜ」を問う**問題を中心に。表面的な事実（What）より、設計判断の理由（Why）の方が理解度を測れる
- **トレードオフ**を問う問題は良い。「もし〇〇でやったら何が困るか？」など
- **境界条件・例外**を問う。「〇〇しないといけないのはどんな時か？」
- **比喩や別領域との対応**で答えられる質問も入れる（OOP vs DoD など）
- 1 問は短く、答えも 1〜3 行で言える粒度に

**避けること：**

- ドキュメントに書かれていない、推測で答えるしかない問題
- 単なる暗記問題（「〇〇のデフォルト値は？」など）
- 同セッション内で同じ概念を 2 回問う

### ステップ 3: 出題範囲を決める

優先順位：

1. **ユーザーが領域を指定した場合**（例：「ストリーミング周りのクイズ」「DSP のクイズ」）
   - 該当する設計ドキュメント 1〜2 本に絞って深堀り
2. **過去に苦手だった領域がある場合**
   - 「次回重点復習候補」または過去の △/✕ 問題のテーマから優先
   - ただし**全く同じ設問**は避け、角度を変えるか発展問題にする
3. **指定なし・履歴なし**
   - プロジェクト全体から横断的に出題
   - 各サブシステムにまんべんなく散らす

問題数のデフォルトは **10 問**。ユーザーが「5問にして」「もっと短く」「最後の1問で」など指示したら従う。

### ステップ 4: 一問一答で進行

#### 出題フォーマット

```
**第N問**

（必要に応じて 1〜2 行の文脈／前置き）

質問：**〇〇は××でしょうか？**（必要ならヒントを括弧で）
```

- 1 問ずつ提示し、ユーザーの回答を待つ。複数問を一気に並べない
- ヒントは「ぼかしすぎず、答えそのものでもない」程度。ユーザーが詰まっていそうなら出す

#### 採点と解説

ユーザーが回答したら、以下のテンプレートで返す：

```
（一言の評価：「正解です！」「惜しい！」「いいところ突いてます」「方向性は合ってます」など）

**判定：◎/◯/△/✕**
**正解：（核心の一文）**

（補足解説：3〜10 行程度。なぜそうなのか、関連する別側面、ユーザー回答が惜しい場合は何が足りなかったか）

---

**第N+1問**
...
```

#### 採点基準

| 判定 | 意味 | 例 |
|------|------|-----|
| ◎ | 完璧。核心を押さえ、付随する理由・背景まで言及 | 「メモリのアロケーションとロック」（理由まで暗黙に含まれる） |
| ◯ | 正解。核心は押さえている | 「キャッシュヒット率が高いから」 |
| △ | 部分正解／方向性は合っている／関連はあるが核心ではない | 「メモリ書き込み領域を使い回せないから」（generation の話と混同） |
| ✕ | 不正解／わからないと答えた | 「わからん」 |

**判定の哲学：**

- 厳しすぎず、優しすぎず。ユーザーが**正しい方向の思考をしているか**を主に見る
- 用語が完全に正確でなくても、概念を捉えていれば ◯
- 「わからん」「知らない」と素直に言われたら ✕。学習機会として丁寧に解説する
- 部分正解（△）は**何が足りなかったか**を必ず明示する

#### 進行の終了条件

以下のいずれかでセッション終了：

- 規定問題数（デフォルト 10 問）に到達
- ユーザーが「終わり」「ここまで」「もう十分」「最後の N 問で」などの意図を示した
- ユーザーが明らかに疲れている／集中力が切れている様子がある場合は、こちらから「ここで一旦区切りますか？」と提案

### ステップ 5: セッション終了時に記録

#### 保存先

```
docs/quiz/{YYYY-MM-DD}.md
```

- 日付は今日の日付（CLAUDE.md の `# currentDate` セクション、なければシステム日時）
- 同日に既存ファイルがある場合：`{YYYY-MM-DD}-2.md`、`-3.md` と連番

#### `docs/quiz/` ディレクトリが無い場合

`mkdir -p docs/quiz/` で作成。プロジェクト直下に作るのが原則。
プロジェクトルートが特定できない／git リポジトリでない場合は、現在のワーキングディレクトリ直下に作る。

#### 記録ファイルのフォーマット

```markdown
# {プロジェクト名 or 一般タイトル} 理解度クイズ — {YYYY-MM-DD}

形式：一問一答（全 N 問）
{オプション：今回のテーマ／出題範囲メモ}

---

## 第1問
**Q. {設問}**

- ユーザー回答：「{回答}」
- 判定：{◎/◯/△/✕}（必要なら短いコメント）
- 正解：{核心の一文}
- 補足：
  - {ポイント1}
  - {ポイント2}

---

## 第2問
...

---

## 結果サマリ

| # | テーマ | 結果 |
|---|--------|------|
| 1 | {一言テーマ} | ◎/◯/△/✕ |
| 2 | ... | ... |

**強い領域**：{◎・◯が多かったカテゴリ}

**伸びしろ**：{△・✕が多かったカテゴリ}

**次回の重点復習候補**：
- {具体的な参照先や領域}
- {〃}
```

**重要：**

- 記録は**ユーザー回答の原文**をできるだけそのまま残す（ニュアンスが学習履歴として価値あるため）
- ただし回答が長すぎる場合は意味を保ったまま要約してよい
- 「次回の重点復習候補」セクションは**必ず書く**。次回セッションがこれを読むため

#### 記録の通知

保存したら以下のように伝える：

```
保存しました：`docs/quiz/{YYYY-MM-DD}.md`
（必要なら：今日の苦手領域は〇〇でした。次回そこから出題します）
```

## エッジケース

### プロジェクトに CLAUDE.md も docs/ も無い

- 出題できる根拠が薄い旨ユーザーに伝える
- README やソースコードから無理に作問するより、「どの領域について確認したいか」を聞いてユーザーから情報を引き出す方が良い
- それでも作問できそうなら進める

### ユーザーが「もっと簡単に／難しく」と要求

- 採点基準を変えるのではなく、**問題の難易度自体**を調整する
  - 簡単に：用語の確認や基本概念
  - 難しく：トレードオフ、エッジケース、別実装との比較

### ユーザーが回答中に脱線・質問してきた

- クイズを一旦中断して質問に答える
- 答え終わったら「クイズ続けますか？」と確認

### 過去ログとの矛盾を見つけた

- ドキュメントが更新されて過去の正解が古くなっていることがある
- 今のドキュメントを正とする。古い記録を訂正する必要はないが、出題時に最新の状態を使う

## 設計の意図（このスキル自体について）

- **一問一答にこだわる理由**：複数問を一気に出すと、ユーザーがまとめて答えてしまい、各問への思考時間が短くなる。1 問ずつのリズムが学習効果を高める
- **記録を残す理由**：苦手領域は時間が経つと忘れる。継続的な追跡で学習が螺旋的に進む
- **採点を ◎/◯/△/✕ の 4 段階にする理由**：3 段階だと「どっちつかず」が中央に集まりすぎる。4 段階で「方向性は合っているが核心ではない」を独立して扱える
- **プロジェクト直下の `docs/quiz/` に保存する理由**：プロジェクト固有の学習履歴がプロジェクトと一緒に持ち運べる。リポジトリにコミットするかは git ignore でユーザーが判断
