## 第1問
**Q. `AuthRepository`（interface）と `AuthRepositoryImpl`（実装）を分けたのはなぜか？**

- ユーザー回答：「インターフェースと実装を合わせてしまうことで、実装の動きにインターフェースが依存してしまうから」
- 判定：△（「依存」という軸は掴めていたが、主語が逆。約束が実装に依存するのではなく、実装が約束に合わせる）
- 正解：`LoginViewModel`（presentation）が Firebase の実装に直接依存しなくなるから
- 補足：
  - `presentation → domain ← data`。domain は誰も知らない中立地帯で、data 側が domain の約束に合わせにいく
  - ViewModel は「`login()` を呼べば `Result` が返る」ことだけ知っていればよく、裏が Firebase でも自前サーバーでもコードが変わらない
  - 実利はテスト。偽の `AuthRepository` を渡せば Firebase 抜きで ViewModel を検証できる

## 第2問
**Q. Google のアカウント選択ダイアログを出す処理だけが `LoginScreen`（画面側）の仕事なのはなぜか？**

- ユーザー回答：「ダイアログを画面に出すには、入力欄に文字が入力されているか、ボタンが押されたかを確認しないといけない」
- 判定：✕（入力チェックの話になっており、必要な「部品」の話に届いていない）
- 正解：ダイアログを出すには `Activity` が必要で、ViewModel は `Activity` を持ってはいけないから
- 補足：
  - `credentialManager.getCredential(context = activity, request = request)` の `activity` が肝
  - 画面回転で Activity は捨てられ作り直されるが ViewModel は生き残る → 古い Activity を握るとメモリリーク／死んだ画面へのアクセスでクラッシュ
  - 役割分担の基準：**Activity が要る仕事＝画面 / データだけで済む仕事＝ViewModel**。ID トークンはただの文字列なので ViewModel に渡して安全
  - `val activity = context as Activity` は §4-⑰ の `as`

## 第3問
**Q. `setFilterByAuthorizedAccounts(false)` にしないと、いつ何が起きるか？**

- ユーザー回答：「アプリに前にログインしたことがあるアカウントでも ID が新しく創られてしまう」
- 判定：✕
- 正解：初回ログイン時に候補が 0 件になり、ダイアログがそもそも出ない（`NoCredentialException`）
- 補足：
  - 「承認済み」＝このアプリで過去にログインしたことがある、の意味
  - `true` のままだと新規ユーザーは永遠にログインできない（鶏と卵）
  - `true` の正しい用途は「ログイン済みの人に 1 タップで再ログインさせる」。実務では true → 失敗したら false の二段構えもある
  - 同じ Google アカウントなら Firebase の uid は同じ

## 第4問
**Q. 一番おおまかな `GetCredentialException` を `catch` の一番上に書くと何が起きるか？**

- ユーザー回答：「一番上で全部受け止めてしまって、下の catch に来ない」
- 判定：◎
- 正解：親分の `catch` が全部受け止め、下の具体的な `catch` に永久に到達しない
- 補足：
  - 例外は上から順に照合され、最初に当たった 1 つだけが実行される（§6-㉕）
  - 実害：ユーザーが自分でキャンセルしただけなのに「ログインに失敗しました」と出る
  - Kotlin ではこれが**コンパイルエラーにならない**（Java は到達不能として弾く）ので、実行して初めて気づく

## 第5問
**Q. `LoginUiState` は `data class` なのに、`SplashUiState` だけ `sealed interface` にしたのはなぜか？**

- ユーザー回答：「メールを入力しているのか、パスワードを入力しているのかは同時に状態を持ちたいから」（＝ログイン側の理由から対比で説明）
- 判定：◯
- 正解：スプラッシュの 3 状態（Loading / Authenticated / Unauthenticated）は同時に成り立たず、必ずどれか 1 つだから
- 補足：
  - `data class` で書くと `isLoading = true` かつ `isAuthenticated = true` という**ありえない組み合わせが表現できてしまう**
  - `sealed` なら `when` の網羅チェックが効き、状態を足したとき対応漏れをコンパイラが指摘してくれる
  - 覚え方：**AND で並ぶ状態は `data class`、OR で分かれる状態は `sealed`**

## 第6問
**Q. なぜ `viewModelScope.launch { }` で包む必要があるのか？ 直接 `authRepository.login(...)` と書けないのはなぜか？**

- ユーザー回答：「viewModelScope.launch に直接メールアドレスとパスワードが渡されてしまうから」
- 判定：✕（引数の受け渡しの話になっており、呼べる場所の制約に届いていない）
- 正解：`suspend` 関数は「待てる場所」でしか呼べず、ViewModel の普通の関数は待てない場所だから。`launch { }` が待てる場所を作っている
- 補足：
  - 直接書くとコンパイルエラー：`Suspend function 'login' should be called only from a coroutine or another suspend function`
  - 待てない場所がある理由＝メインスレッドで待つと画面がフリーズするため。Kotlin は文法レベルで壁を作っている
  - `viewModelScope` を選ぶ理由＝ViewModel が捨てられると走行中の処理も自動で打ち切られ、死んだ画面への結果配達を防げる
  - `launch` に渡っているのは `{ }`（作業メモ／§1-⑥）だけで、`launch` 自身は email の中身を知らない

## 第7問
**Q. Repository が例外をそのまま投げず、`Result<User>` に詰め替えるのはなぜか？**（※ヒント使用）

- ユーザー回答：「try/catch を書き忘れてアプリが落ちる」
- 判定：◯
- 正解：例外は「失敗しうる」ことが型に現れないため、呼ぶ側が `try/catch` を忘れてもコンパイルが通り、実行時に落ちるから
- 補足：
  - `: User` という宣言を見ても失敗の可能性は分からない。`Result<User>` なら型が宣言している
  - もう1つの効果：Firebase 固有の例外型（`FirebaseAuthInvalidCredentialsException` 等）を Repository に閉じ込められる → 第1問と同じ話
  - ◎ の一言は「**失敗の可能性が型に書いてあるので、コンパイラが対処を促してくれる**」

## 第8問
**Q. `LoginViewModel` の中で `AuthRepositoryImpl(...)` を自分で作ると何が困るか？**

- ユーザー回答：「画面の頭脳が Firebase の都合に縛られてしまう」
- 判定：◯（第1問の学びを応用できた）
- 正解：ViewModel が実装クラスを名指しすることになり、interface に分けた意味が消える
- 補足：
  - ① テストで差し替えられない ② 実装の作り方が変わると `new` している全ファイルに波及（Hilt なら `RepositoryModule` の 1 箇所）③ 画面ごとに別インスタンスができる（`@Singleton` で共有できない）
  - DI ＝「材料を自動で届けてくれる仕組み」の**「自動で」の価値**がここ

## 第9問
**Q. アプリを再起動してもログイン状態が残るのはなぜか？ `currentUser` は何を見ているのか？**

- ユーザー回答：「わからない」
- 判定：✕
- 正解：Firebase Auth SDK がログイン時に受け取った**トークン**を端末内に保存しており、`currentUser` はそれを見ている
- 補足：
  - **ID トークン**（本人証明・有効期限約1時間）と**リフレッシュトークン**（交換用・長期間）の 2 種類が発行される
  - 保存コードを書いていないのに残るのは SDK が裏でやっているから。保存先はアプリ専用領域
  - `currentUser` はサーバーに問い合わせない（ローカル参照）ので `suspend` 不要・機内モードでも動く
  - `logout()` はこの保存トークンを消す → 次回起動で `null` になりログイン画面へ

### 派生した質問：「パスワードもハッシュ化して保存すればいいのでは？」
- ハッシュ化は**サーバーがパスワードを保管する技術**であり、端末がログイン状態を維持する用途には使えない
- ハッシュを送って認証するなら、そのハッシュ自体がパスワードと等価になる（盗まれたら終わり）
- トークンの優位点：**有効期限がある / サーバー側から無効化できる（端末紛失時）/ 被害がこのアプリに限定される**
- Google ログインではアプリが Google のパスワードを一度も受け取らない。「パスワードは発行元だけが知り、アプリには身分証だけ渡す」が現代の認証の基本形

## 第10問
**Q. `setServerClientId` に Android 用（client_type: 1）ではなくウェブ用（client_type: 3）のクライアント ID を渡すのはなぜか？**

- ユーザー回答：「Google は Web をクライアントとしてログインなどをするから」
- 判定：✕（Web が絡むところまでは嗅ぎ取れていたが、理由が逆向き）
- 正解：ID トークンを最終的に受け取って検証するのが Firebase Auth の**サーバー**で、そのサーバーがウェブ用クライアント ID で登録されているから
- 補足：
  - ID トークンには「誰宛てか」を示す宛先欄（audience）が刻印される。`setServerClientId` はその宛先の指定。メソッド名の `Server` がそれを示している
  - 流れ：アプリが宛先を指定して要求 → Google が刻印して発行 → アプリは素通しで Firebase へ → **Firebase のサーバーが**照合
  - Android 用 ID は「このアプリが正規のものか」を署名（SHA-1）と結びつけて識別するもの。サーバーではなくアプリ本体を指すので宛先欄には書けない
  - **検証はサーバーの仕事**。アプリ側で成功判定すると改造アプリから偽装できる → Phase3 の「認可はセキュリティルール＝サーバー側でやる」と同じ考え方
