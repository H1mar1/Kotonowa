## 第1問
**Q. ログアウトを「① 通知の住所（FCM トークン）を外す → ② サインアウト → ③ onDone() で画面を移す」の順にしたのはなぜ？**

- ユーザー回答：「画面のちらつき防止」
- 判定：✕
- 正解：画面が履歴から消えると ViewModel も捨てられ、viewModelScope の中の通信（①）が途中で打ち切られるから
- 補足：
  - 打ち切られると、ログアウトした端末にプッシュ通知が届き続ける
  - ② を先にすると名刺を書き換える権限が無くなる。Step 28 の「saveUser は isLoginSuccess より前」と同じ原則（画面が消える前に通信を終わらせる）

## 第2問
**Q. 確認メールのリンクを押したあと getIdToken(true) が要るのはなぜ？**

- ユーザー回答：「リンクだけでは確認が終わらない」
- 判定：✕（確認自体はリンクを押した時点でサーバー側で済んでいる）
- 正解：ルールが見る email_verified は通行証（ID トークン）に焼き込まれた値なので、作り直すまで古いまま
- 補足：
  - 通行証＝発行時点の情報を印刷したカード。名簿が変わっても印字は変わらない
  - true は「手元のカードを使わず新しく発行して」

## 第3問
**Q. members の名簿があるのに、calendars に memberUids 配列も持たせたのはなぜ？**

- ユーザー回答：「子から親を引けないため」
- 判定：◯
- 正解：サブコレクションから親を逆引きできないので、whereArrayContains の 1 回で部屋ごと取るため
- 補足：
  - ルールも `uid in memberUids` の 1 行で書ける
  - 二重持ちなので人の出入りは runBatch で同時に書く。Kotlin の Calendar には持たせない

## 第4問
**Q. 名簿の行を作るルールで、部屋の ownerUid を get ではなく getAfter で確かめたのはなぜ？**

- ユーザー回答：「get は自分の書類しか読めない」
- 判定：✕（get でも別の書類は読める。isMember / myRole がそう）
- 正解：部屋と名簿は runBatch で同時に書かれるので、書き込み前（get）にはまだ部屋が無く必ず断られる。getAfter は書き込み後の状態を読む
- 補足：
  - 招待の承認（36-G）は get（前は pending）と getAfter（後は accepted）の両方を見ている

---

## 第5問
**Q. `.update("role", "role" to 値)` や `.set(addItem(item))` がビルドを通ってしまったのはなぜ？**

- ユーザー回答：「Kotlin は実行時に型を確かめる」
- 判定：✕（Kotlin はビルド時に型を確かめる）
- 正解：Firestore の命令が値を Any で受け取るので、中身がずれていてもコンパイラが止められない
- 補足：
  - 対策は「Firestore に渡す直前の行を、誰の・どの項目に・何をする と声に出して読む」
  - 型を具体的に書いた場所（Flow<List<Calendar>> など）ではコンパイラが止めてくれた

## 第6問
**Q. Cloud Functions が notification ではなく data だけで送るのはなぜ？**

- ユーザー回答：「通知を消すため」
- 判定：✕（data だけでも画面に通知は出ている）
- 正解：data だけなら、アプリが裏にいても必ず自分の onMessageReceived を通り、通知の出し方を 1 か所でそろえられる
- 補足：
  - notification つきだと、裏にいるときは Firebase が代わりに出し、自分の係が呼ばれない

## 第7問
**Q. updatedBy を必須にしたとき、ルールを先に公開するとどうなる？**

- ユーザー回答：「古いアプリの保存が断られる」
- 判定：◯
- 正解：updatedBy を送らない古いアプリの作成・編集がすべて断られる
- 補足：
  - 「新しいアプリ × 古いルール」は問題ない（余分な項目は素通り）ので、アプリが先
  - Step 46 も「アプリ → 関数 → ルール」の順

## 第8問
**Q. タスク一覧の頭脳で flatMapLatest を使うと何がうれしい？**

- ユーザー回答：「タスクを並べ替えてくれる」
- 判定：✕（並べ替えは画面の sortedBy）
- 正解：入っているカレンダーの一覧が変わるたびに、前の見張りを止めて新しい一覧で張り直してくれる
- 補足：
  - Latest＝一番新しい「カレンダーの一覧」だけ生かす。Step 23 の observeJob?.cancel() → collect を 1 語でやる道具（§2-(143)）

## 第9問
**Q. load() に catch (e: CancellationException) { throw e } を足さないとどうなる？**

- ユーザー回答：「「読み込めません」が出る」
- 判定：◯
- 正解：止めた合図が catch (e: Exception) に吸い込まれ、削除しただけで失敗扱いになる
- 補足：
  - CancellationException は Exception の子ども。具体的な方を先に受ける（§6-㉕。前回 ◎ の知識）

**Q. Repository を interface で受け取っておくと、テストで何がうれしい？**
